# ZeeAI Terminal —— 产品方向建议（v0.1.7 基线）

> 这是**产品视角**的第二份文档。技术优化建议在 `docs/review/tech-optimization-proposals.md`。
> 本文不改任何代码，只回答三个问题：**这个产品现在是什么、它的真实优势在哪、下一步该往哪走。**
> 依据：`README.md`、`docs/design.md`、`docs/decisions.md`（13 轮迭代记录）、以及本轮对代码的现场审查。

---

## 0. 一句话判断

> **你现在做的不是"又一个终端"，而是一个「AI 任务驾驶舱」——只是目前驾驶舱的仪表盘只装了一半。**
>
> 终端功能（SSH / tmux / SFTP / 串口 / ADB / 本地 shell）已经把"能干活"这件事做完了，
> 真正没人替你解决的是：**我让 AI 在远端跑了一个长任务，我怎么知道它跑完了、跑得怎么样、产出了什么。**
> 这件事你已经做了 v1，而它还差最后一段闭环。**产品资源应该继续压在这里，而不是继续铺终端功能。**

## 1. 现状盘点

### 1.1 能力矩阵

| 领域 | 已有 | 成熟度 |
|---|---|---|
| 远程终端 | SSH、密钥/密码、跳板机、断线重连、tmux 持久会话 + 快捷操作面板 | 高 |
| 远程文件 | 真 SFTP（浏览/上传/下载/递归/重命名/删除）、MD/HTML 预览 + 下载 | 高 |
| 本地终端 | PowerShell / CMD / WSL、管理员模式（整体提权 + 单独开管理员窗） | 高 |
| 设备 | 串口（自建连接参数）、ADB（内置 platform-tools）、Fastboot | 中高 |
| 代码 | Git 面板（暂存/提交/历史/diff/分支） | 中 |
| 组织 | 服务器管理、会话历史、工作区恢复、分屏（2/3/4 格）、标签拖动排序 | 中高 |
| 外观 | 13 套界面主题 + 15 套终端配色、按终端类型分别配置、关键字高亮 | 高 |
| **AI** | Agent 面板、任务看板 v1、通知分级、产物清单 v1、Token 显示 | **中（这是重点）** |

### 1.2 真实的差异化在哪

把上面这张表拆开看，你会发现：**除了"AI"这一列，其余每一列都有成熟竞品做得很好了**
（MobaXterm 的会话管理、SecureCRT 的日志、Windows Terminal 的本地体验、VS Code Remote 的文件）。
继续在这些列里加功能，边际收益是递减的。

而 AI 这一列，你手上有的东西是**别人没有的**：

- 从 **Codex 会话日志（rollout jsonl）** 里读出来的任务状态，比"进程还在不在"精确得多：
  `task_complete`、`last_agent_message`、`duration_ms`、`token_count`、`function_call`；
- **信号分层**（App 自己启动的 > 远端 tmux 窗格 > 远端 ps > 本机进程表）——这是一套真正的工程判断，
  包含"WSL 里的进程 Windows 侧看不见""CMD 没有脚本钩子只能给状态""TUI 拿不到百分比所以不做进度条"
  这些踩出来的取舍；
- **产物清单**：用「会话 cwd + 这一轮的时间窗」反推 AI 写了哪些文件。

> 这三个东西加起来，就是"**AI 在远端跑，我在本地随时看状态和产物**"的雏形。
> 这也是你在 `docs/decisions.md` 里明确写过的：**这一步的优先级高于花哨的状态展示。**

### 1.3 但闭环还差一段

现在这条链路的实际体验是：

```
启动任务 ✅   →  看到在跑 ✅   →  跑完通知 ✅   →  看到产物 ⚠️   →  验收/继续 ❌   →  事后回溯 ❌
```

- **产物**：找到了（T-12 会漏报，技术上要修），但只是「📄 按钮列表」，
  点开是预览，没有"这轮改了哪个文件的哪一段""和上一轮比变了什么"。
- **验收 / 继续**：任务完成后，看板不会告诉你"下一步该干什么"，
  你还得自己切回那个终端敲字。
- **事后回溯**：看板只显示**当前这一轮**。昨晚跑了 5 个任务，今天早上你**什么都看不到**。

**结论：AI 任务缺的不是"更多状态展示"，而是"任务生命周期的完整记录与可操作入口"。**

## 2. 从 13 轮迭代里读出来的用户画像

`docs/decisions.md` 记了 13 轮，每一轮几乎都由一条截图反馈驱动。把它当用户研究材料读，
能看出很清晰的模式：

| 观察 | 证据 | 产品含义 |
|---|---|---|
| 你是**多服务器 + 多会话**的重度用户 | 反复出现"LZ 服务器下建了好几个会话""同时开多个终端" | 会话**组织**能力比会话**创建**能力更重要 |
| 你最烦的是**噪音**，不是缺功能 | "提示文字太多、看的人心累""能不能简洁再简洁""甚至不要提示"（出现了至少 5 次） | **"少说"是一个产品能力**，应该当成需求来管理 |
| 你反复被**状态不同步**咬到 | "左侧显示已打开但其实关了""标签名和历史名不一样""AI 没任务却显示 9 条消息""只显示普通 shell 2" | 任何"两份状态各存一份"的地方都会出 bug → 应该收成**单一数据源** |
| 你要的是**可回溯**，不只是可看见 | "我翻上去发现变了""为什么没提示我去看那个 Markdown""我还需要看到全名" | 时间线 / 历史 / 可回看 是核心诉求 |
| 你对"能不能真的跑起来"很敏感 | "为什么点了安装没重启""分片下载出事故""不要出错/不要死锁/不要下错" | **可靠性本身就是产品功能**，不是工程细节 |

**一句话画像**：*一个人同时管好几台机器、在好几台机器上跑 AI 编码 agent、看屏幕的时间少于不看屏幕的时间。*

## 3. 三条主线（建议的资源分配）

### 主线 A · AI 任务驾驶舱（**60% 精力**，差异化护城河）

把"AI 任务"从"一个面板"做成"一条时间线"。

### 主线 B · 多机会话工作台（**25% 精力**，基本盘）

解决"我有 3 台服务器、每台 4 个会话，我找不到我要的那个"。

### 主线 C · 不添乱（**15% 精力**，体验底线）

把噪音、误报、状态不一致这些"每天都在消耗信任"的东西清干净。

## 4. 机会清单（供你挑）

每条给 **价值 / 成本 / 风险** 三个维度，你可以像挑技术条目一样直接点编号。

### 主线 A · AI 任务驾驶舱

#### G-01 【最高价值】AI 任务时间线（任务历史 + 归档）

**现状**：看板只有"当前这一轮"，昨天的任务今天查不到。`AiTaskRegistry` 是内存里的，重启即失。

**做什么**：把任务卡片落成**持久化的时间线**——每条记录 `工具 / 环境 / 服务器 / 项目目录 /
开始时间 / 耗时 / 结束状态 / 最后一句话 / 产物列表`，支持按时间、服务器、项目筛选，
点进去能看到完整的一轮内容。**这是"我离开电脑再回来"的真正答案。**

**价值**：高（直接命中你"离开之后要知道发生了什么"的核心场景）
**成本**：M（后端加持久化 + 前端加列表视图）
**风险**：低。数据来源已经有了，只是没存下来。

---

#### G-02 【高价值】产物清单 v2：从"找到"到"看懂"

**现状**：只能按时间窗 + cwd 猜出"这一轮动过哪些文件"，给一排 📄 按钮。

**做什么**：

1. 精确化（OSC 133 shell 集成：A/B/C/D;exit）——知道这一轮**跑了哪条命令、退出码是多少**，
   于是产物的时间窗可以精确到命令级，而不是靠 ±5 秒的估算；
2. 可读化——产物按类型分组（代码 / 文档 / 日志 / 图片），Markdown 和 HTML 走已有的预览；
3. **可对比**——如果它是个已有文件，给一个"这一轮改了什么"的 diff（Git 仓库直接 `git diff`，
   非 Git 目录给 mtime + 大小变化）。

**价值**：高（你原话："这一步才是闭环"）
**成本**：M–L（OSC 133 需要给 PowerShell profile / bash PROMPT_COMMAND 注入，你们已经为 OSC 7 做过一次，同一套做法）
**风险**：中。注入要小心不能污染用户的 shell 配置（你们上次 OSC 7 的做法是"不改服务器任何 rc 文件"，这次要保持）。

---

#### G-03 任务结束后的"下一步"入口

**现状**：卡片告诉你"跑完了"，然后……没有了。

**做什么**：卡片上直接给三个动作 —— **「回到这个终端」**（切到那个 tab）、
**「看产物」**（已有）、**「标记已阅」**（清掉红点/横幅）。
将来可以加「继续这个任务」（把一条预设指令敲进那个终端——注意：**不是模拟按键去做 tmux 操作**，
只是往那个会话写一行命令，和现在"一键启动 AI"是同一套机制）。

**价值**：中高（把"看到"变成"能动手"）
**成本**：S–M
**风险**：低

---

#### G-04 通知体系的产品化（在已有三层上补两件事）

**现状**：红点/数字（活动栏）→ 可选闪任务栏 → 状态栏闪烁横幅。你已经定了这个分层，方向是对的。

**补什么**：

1. **数字要对得上事实**——历史上出现过"没任务却显示 9 条"（`docs/decisions.md:1038` 记了根因）。
   产品上应保证：**Badge 上的数字 = 真的需要你处理的条目数**，而不是"通知过的次数"。
2. **免打扰 / 过滤**——夜里跑 20 个任务不用弹 20 次；可以按"只通知失败/需要批准""免打扰时段"
   过滤（声音要不要加由你定，我倾向不加，避免变成噪音源）。

**价值**：中高（你的核心诉求之一）
**成本**：S
**风险**：低

---

#### G-05 Token 与用量的产品化（你已定：**以兆为单位，不折算钱**）

**现状**：卡片上显示 `token 1.2M · 上下文 43% · 上一轮 3 分 20 秒`。

**做什么**：把用量**累积**起来——按服务器 / 项目 / 工具统计"今天用了多少 M"，
配一条按天的简单曲线。**不折算成钱**（你明确说过），只做"我能看见自己用了多少"。

**价值**：中（对重度用户是刚需，但不像 G-01 那样是"没有就断链"）
**成本**：S–M（数据已经在快照里了）
**风险**：低（要说明"这是 agent 报的累计值，不一定等于账单"）

---

### 主线 B · 多机会话工作台

#### G-06 会话的组织：分组、搜索、批量

**现状**：服务器分组 + 会话历史列表，但没有**搜索**，不能批量开关，会话多了会乱。

**做什么**：侧栏加搜索框（按名字/主机/目录过滤）；服务器支持标签（prod / test / 客户名）；
"一键打开这台机器的全部常用会话"；会话按最近使用排序（时间标志你已经要求去掉了，
但**排序依据**还是可以保留）。

**价值**：中高（你的重度使用方式决定）
**成本**：M
**风险**：低

---

#### G-07 首次使用 / 迁移体验

**现状**：要手工一条条加服务器。

**做什么**：导入 `~/.ssh/config`、导入 PuTTY / MobaXterm 的会话；首次启动做一次"环境体检"
（有没有 OpenSSH 客户端、有没有 Git、WSL 装没装、串口驱动），把结果放**状态栏**（不是浮层）。

**价值**：中（对你本人价值一般，对"给别人用"价值高）
**成本**：M
**风险**：低

---

#### G-08 高亮 v2（已在你自己的路线图上）

正则支持（**必须限量限长**，否则 `.*` 会卡死渲染——你们自己已经写进约束了）、
按服务器 / 串口设备分规则集、命中关键字只写底部状态栏告警、历史着色（decoration 路线）。

**价值**：中（串口场景下"出现 panic 就提醒"很实用）
**成本**：M
**风险**：中（正则性能必须有硬上限，否则会变成"打开终端就卡"）

---

### 主线 C · 不添乱

#### G-09 把"文字噪音"当成一个可验收的需求

你已经为这件事提过至少 5 次。建议**立一条产品规则**并写进 README：

> 任何界面文案，默认不出现；只有"用户此刻必须知道才能做对下一个决定"的信息才允许出现，
> 且必须能放到状态栏或悬停提示里。

顺带做一次"文案审计"：遍历所有提示，逐条问"删掉它，用户会不会做错事？"——不会就删。

**价值**：中高（这是你每天都在感受的东西）
**成本**：S（纯删减）
**风险**：低

---

#### G-10 状态一致性：收敛到单一数据源

第 13 轮那条"左侧显示已打开、实际关了""标签名 ≠ 历史名""普通 shell 永远只有一条"
——根因都是**同一份事实存了两份**。产品上建议立规矩：

> 会话的"身份/名字/是否打开"只允许有一个权威来源（前端 store 或后端，二选一），
> 其它地方一律是它的投影。

**价值**：中高（这类 bug 会反复出现，值得从结构上掐掉）
**成本**：M（技术重构，属技术文档 T-32 的一部分）
**风险**：中（重构期容易引入新问题，要配合回归清单）

## 5. 明确**不建议**做的事

| 不做 | 理由 |
|---|---|
| 差分包更新 | 技术上收益小、风险大（见技术文档第 1 节的 FAQ）；**省流量的正确做法是先砍 17.6MB 的 platform-tools** |
| 中央浮层 toast | 你的硬规则；而且它确实会挡视线 |
| AI 任务的进度条 | TUI 拿不到百分比，做了就是假信息 |
| 继续铺终端功能（更多协议、更多面板） | 边际收益递减，而且会违背你自己定的"别把程序做臃肿" |
| 移动端原生 App | 成本巨大；先做只读网页版（G-11）验证需求 |
| 为 CMD 做深度集成 | 你已明确"标成仅状态即可，别为它投入" |

## 6. 建议的版本节奏（三档，供你选）

### 方案 ①「稳一版再往前走」（推荐）

| 版本 | 内容 | 主题 |
|---|---|---|
| **v0.1.8** | 技术文档套餐 A/B（升级链路修复 + 体积砍半 + 看板不漏报）+ G-09 + G-04 | **把地基修稳、把信任找回来** |
| **v0.2.0** | G-01 + G-02 + G-03 | **AI 任务闭环**（这一版才是真正的新故事） |
| **v0.3.0** | G-06 + G-08 + G-05 | 多机工作台 + 高亮 v2 + 用量 |

**为什么先修地基**：一键升级现在是**必然失败**的（技术 T-01），而你所有对外宣称的
"一键升级"都建立在它上面。先把这个和体积问题处理掉，再讲新故事，用户信任的曲线才是向上的。

### 方案 ②「先讲新故事」

直接把 G-01 + G-02 做到 v0.2.0，地基问题穿插修。
适合：**只有你一个人用**、不急着给别人装。风险是"升级还是坏的"这件事会一直悬着。

### 方案 ③「只修不加」

只做技术套餐 A，做完停下来用一段时间，把真实痛点攒够了再规划 v0.2.0。
适合：你觉得现在功能已经够了，缺的是稳定。

## 7. 风险与依赖（要提前认下来的）

1. **对 Codex 内部日志格式的强依赖**（最大风险）。
   现在的状态判定全部建立在 `~/.codex/sessions/**/rollout-*.jsonl` 的字段上
   （`task_complete` / `token_count` / `function_call`）。**这个格式哪天变了，看板就会静默失效。**
   产品上必须做两件事：① 一层"适配 + 降级"（读不到日志时明确显示"数据源不可用"，
   而不是显示"暂无运行中的 AI"）；② 每次适配新版本后把样本存成回归样本（已有单测雏形）。
2. **`needs-approval`（等你批准）至今没有真实样本**——这条状态在产品上是"最重要的那条"
   （它代表"卡住了等你"），但代码里只有人造单测。建议尽快在测试机上抓一份真样本。
3. **Windows-only** 决定了市场规模上限。如果哪天真要给别人用，这是第一个要重新评估的决定。
4. **自研更新链路**的维护成本已经被证明偏高（0.1.5 事故 + 这次发现的 P0）。
   长期看值得评估 Tauri 官方 updater，把"校验/静默安装/重启"交给上游。
5. **AI 工具生态是黑盒**：codex / claude / aider 的 TUI 都不提供结构化进度。
   所以产品叙事要克制——**能说的说，不能说的不要编**（这也是你不做进度条的原因）。

## 8. 一页纸总结

- **产品身份**：不是终端，是「AI 任务驾驶舱 + 多机工作台」。
- **最大机会**：把 AI 任务做成**可回溯的时间线 + 可操作的闭环**（G-01 / G-02 / G-03）。
- **最大隐患**：一键升级现在是坏的，且对 Codex 日志格式强依赖（T-01 / 风险 1）。
- **最该克制的**：继续铺终端功能、继续加提示文字。
- **下一步建议**：v0.1.8 稳地基 → v0.2.0 做闭环 → v0.3.0 做多机。
