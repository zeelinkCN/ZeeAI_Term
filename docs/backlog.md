## [ ] 浅色主题下，设置面板里有些控件是"深底深字"，看不清

**报的日期**：2026-09-29（用户截图：设置 → 外观，主题选 VS Code 浅色）
**用户原话**：*"调成浅色主题配色的话，设置里面会有很多个类似于下面这个深灰色的框，
导致有些字体或者按钮看不清描述。这个在下一班的时候帮我改掉。暂时不修改源码，
你先记下来这个问题，下一次做新问题、新 feature 的时候再一并改。"*
**当时的处理**：只记录，**没有改任何源码**。

### 现象

切到浅色主题后，设置面板里出现几块深灰的"框"：

1. **普通按钮**（截图里那颗「终端配色与关键字高亮…」）：底色仍是深灰 `#2a2d2e`，
   文字用的是浅色主题的深色 `--fg` → **深底深字，几乎读不出来**。
2. **两个滑块**（终端字体大小 / 终端回滚行数）：轨道是深灰，压在白色面板上很突兀；
   拖过的部分和没拖过的部分也分不出来。

### 定位（2026-09-29 只读排查，未改动）

- `src/styles.css:534` —— `.btn { background: #2a2d2e; color: var(--fg); }`
  这里**写死了深色底**；浅色主题只覆盖了 `--fg`，于是变成深底 + 深字。
- `src/styles.css` 里同样的硬编码深底还有约 20 处（`#3c3c3c` / `#2a2d2e` / `#1e1e1e` 等），
  例如 572 / 767 / 833 / 1981 / 2159 / 2381 / 2541 行。
- **完全没有** `input[type=range]` 的样式 → 滑块用的是浏览器默认外观，不跟主题走。
- 浅色主题（`.app.light ...`）是"按组件打补丁"式覆盖：只覆盖了
  `side-btn` / `side-allbtn` / `tmux-dock` / `tmux-win` / `tt-item` / 各种 input 等，
  **没有** `.app.light .btn` / `.app.light .mini-btn`。

### 影响范围

不止截图里那两处 —— 凡是用了硬编码深底、又没被浅色覆盖的控件都会中招。
需要按下面"建议做法"做一次**全量清点**，而不是只补 `btn`。

### 建议做法（下次做）

1. 给这两个颜色收进主题变量：`--btn-bg` / `--btn-bg-hover`，深色一套、浅色一套；
   把 `.btn`、`.mini-btn`、`.tmux-*`、`.tt-item` 等硬编码底色换成变量（或直接复用现有 `--panel`）。
2. 补 `input[type=range]` 的样式：轨道用 `var(--border)`、已填充段用主题强调色、
   滑块用 `var(--fg)` 或强调色 —— 深色/浅色都跟着走（也可以先用 `accent-color` 过渡）。
3. 清点一遍：`rg "background: #(1|2|3|4)[0-9a-fA-F]{5}" src/styles.css`，
   每一处都问一句"浅色主题下它是什么样"。

### 验收标准

- 切到任意浅色主题，逐页翻设置（外观 / 终端与会话 / 会话日志 / 通知 / 更新与关于），
  **没有任何一处是"深底深字"或"浅底浅字"**；按钮、滑块、下拉、色块都能看清。
- 深色主题不回归。
- 在 `scripts/fe-smoke.mjs` 里加一条断言：切到浅色主题后，设置面板里所有
  `.btn` / `input[type=range]` 的计算样式（背景与文字）对比度达标 —— 让这类问题以后能被自动拦住。

### A. 本机那条：读到了**桌面版 Codex 自己的会话日志**（真错误，必须修）

#### 现象

用户补的截图里，看板下半部分「最近任务（2）」写着：

```
09/29 22:04 · 本机 PowerShell · Zee…      1 分 25 秒
记下了（提交 `22495dc`，源码零改动），…
📄 backlog.md      [切过去]
```

那条"任务"的内容，正是**本助手（桌面版 Codex）当时给用户的回复**，
挂着的产物正是**我当轮改的那个文件**。等于把"AI 助手在桌面端干的活"
记成了"用户在本机 PowerShell 里跑的任务"。

#### 根因（已定位到函数）

`src-tauri/src/core/ai_sessions.rs:814`

```rust
/// 本机：%USERPROFILE%\.codex\sessions 下最新的那个 rollout，读它的尾巴
pub fn local_snapshot() -> Option<AiSessionSnapshot> {
    let root = %USERPROFILE%\.codex\sessions;
    let newest = newest_rollout(&root, 0)?;   // ← "最新那份"不区分是谁写的
    ...
}
```

它取的是**本机 `~/.codex/sessions` 里最新的一份 rollout**，而桌面版 Codex 自己的会话日志
就躺在同一个目录里。实测那份最新日志（37 MB）的头部：

```
payload.originator = Codex Desktop      ← 关键判别字段
payload.source     = vscode
payload.model_provider = custom
payload.cwd        = <桌面端会话的工作目录>
```

`commands.rs:1800` 的 `ai_session_snapshot` 对本机 PowerShell 会话走 `local_snapshot()`，
于是这份日志里的 `task_started` / `task_complete` / `token_count` / `agent_message`
全被当成"当前会话（本机 PowerShell）里的那轮 AI 任务"，产物再去 `cwd` 下扫一遍
（`ai_task_artifacts`）—— 连 `📄 backlog.md` 都挂上去了。

#### 为什么必须修

1. **归错环境**：那不是用户 PowerShell 里的任务，桌面版 Codex 也不在那个会话里跑；
2. **把助手自己的活摊给用户看**（用户原话："这属于你能看到别人正在工作的内容"）；
3. **切不过去**：点「切过去」只会跳到那个 PowerShell 标签，那里根本没这回事；
4. 桌面端会话日志动辄几十 MB，每次去读它的尾巴也是白费 IO。

#### 建议做法（按推荐顺序）

1. **按 `originator` 过滤（首选，最准）**：解析 rollout 头部 `session_meta`，
   `originator` 含 `Desktop`（或 `source == "vscode"`）的**一律不读** ——
   那是桌面客户端自己的日志，不是"终端里敲出来的 codex"。
   用户在自己 PowerShell 里跑 `codex` 时 originator 是别的值，不受影响。
2. **加"是不是这个会话的"校验**：只认 `payload.cwd == 当前会话 cwd`
   且 rollout 的 mtime **晚于该会话建立时间**的那一份（现在这两个条件一个都没有）。
3. 最省事的兜底：**本机 PowerShell / CMD 干脆不读 rollout** ——
   "本机有没有 AI 在跑"已经由进程扫描覆盖，token/耗时这点信息不值得换来这种误报。
   （WSL 仍可读：它有独立文件系统，读的是 WSL 里的 `~/.codex`。）

#### 验收标准

- 桌面版 Codex 正在干活时，本机 PowerShell 会话的看板/时间线**一条都不出现**，
  产物列表里也不会冒出我们改过的文件；
- 用户在自己 PowerShell 里跑 `codex`，仍然能正常显示（含 token/耗时）；
- 回归用例：拿一份 `originator=Codex Desktop` 的 rollout 头部喂给筛选逻辑，断言**被拒**；
  换一份 `originator=codex_cli*` 的，断言**通过**。

### B. 远端那两张卡：陈旧 herdr 窗格占位 + 面板标题错位（观感问题，跟着一起做）

放大截图，那两张卡**都写着"远端"**，来源是 `herdr 状态`：

| 卡片 | 标签 | 副标题（卡片第 2 行） |
|---|---|---|
| OpenAI Codex CLI | 远端 · **空闲** | `lz · lz w1Q:p1 · 已开在「lz · lz w1Q:p1（接管…` |
| OpenAI Codex CLI | 远端 · **已完成** | `lz · lz w1T:p1 · 已开在「lz · herdr w1T:p1（接…` |

这两张卡本身**没错**（是用户自己跑的窗格，卡片上也有「切到标签」），问题在呈现：

1. **面板标题跟着当前会话走**：标题写「AI Agent · PowerShell」、来源写「本机探测」，
   下面却列着**远端**的卡 —— 这是让用户以为"它探测到我的 PowerShell 里有 Codex"的
   直接原因。改成固定的「AI 任务看板」，每张卡自带环境/服务器/窗格归属。
2. **不活跃的窗格不该占卡片位**：`空闲` / `已完成` 是"窗格现状"不是"任务"。
   默认只显示 `运行中` / `等你处理`，其余收进一行折叠（「另有 N 个不活跃的窗格」），
   超过 30 分钟没动静就不显示。
3. **通知口径**：只在"等你处理（blocked）"和"产出新文件"时通知；
   `空闲 / 已完成` 一律不通知。
4. **动作按钮跟状态一致**：能一步切过去的才给「切到标签」，其余给「开观察窗」。
5. 顺手清掉 `lz · lz` 这种重复服务器名的脏标签（`herdrShortLabel` 那条修法的延伸）。
